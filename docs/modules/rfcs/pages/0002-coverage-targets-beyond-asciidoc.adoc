= RFC 0002: Coverage targets beyond AsciiDoc

Status: *draft* -- Extends xref:0001-spec-coverage.adoc[RFC 0001]. Every
rule of RFC 0001 stands; this RFC generalizes one noun in it -- the
_measured page_ becomes a _measured target_ -- and adds what follows from
that.

Retiring the interim `sdd` tools requires it: in `asciidoc-parser`, `sdd`
measures not only the AsciiDoc language documentation but also the
Asciidoctor Ruby test suite, which is vendored verbatim and ported test by
test. RFC 0001 as written cannot take that suite over, and it cannot
measure a specification that exists only as HTML. Both cases are covered
here.

== Why RFC 0001 stops at AsciiDoc

RFC 0001 makes the block the unit of coverage and assumes, without saying
so, that every measured artifact is an AsciiDoc page in the site's content
catalog:

* blocks and their source spans come from `asciidoc-parser`;
* excerpts match the block's `.adoc` source text;
* claim paths resolve against _catalog pages_;
* structural defaults are stated in AsciiDoc terms (listings, block
  titles, admonitions);
* the overlay shades the rendered page, which exists because the page is
  AsciiDoc.

Two real targets break every one of those assumptions.

*The Asciidoctor reference suite.* `asciidoc-parser` vendors
`test/*_test.rb` from Asciidoctor v2.0.26 under `ref/asciidoctor/test/`
(25 files, 2,783 `test` cases, MIT) and ports them one file at a time.
Each Ruby test is reproduced inside a `verifies!` block above its Rust
port, exactly like a spec paragraph (about 1,600 such blocks today), and
`sdd` emits per-line coverage keyed by the `.rb` path, which Codecov
reports as its own "Asciidoctor reference coverage" component. The Ruby
file is not AsciiDoc, is not a catalog page, and has no blocks in RFC
0001's sense -- yet it needs claims, states, a denominator, Codecov lines,
and a rendered view no less than a spec page does.

*A specification published only as HTML.* Same problem from the other
side: prose with a clear block structure (paragraphs, list items, tables,
sections with ids) that we did not author and cannot obtain as `.adoc`.

Both share one shape: a non-AsciiDoc artifact that we can nonetheless
segment into addressable blocks with text a human can quote.

== Design overview

Everything in RFC 0001 downstream of "parse the page" depends on exactly
four facts about a measured artifact: a path, a list of blocks with line
spans and quotable text, section anchors for `#anchor` scoping, and a
default classification per kind of block. Name that the *target contract*
(<<_the_target_contract,§3>>). An AsciiDoc page is one implementation of
it; a *target adapter* implements it for each other format
(<<_adapters,§4>>). Claims, sidecars, the six states and their
precedence, rollup, `lint`, and the Codecov projection are unchanged and
are never made format-aware.

Two routes were considered for getting a foreign artifact under that
contract:

. *Native adapters* -- segment the artifact in its own terms (a Ruby test
  case is a block; an HTML `<p>` is a block), and match excerpts against
  its own text.
. *Transliteration* -- convert the artifact to AsciiDoc once, commit the
  result, and apply RFC 0001 to it unchanged.

This RFC adopts *native adapters as the source of truth* and uses
transliteration only for *display*:

* Excerpts quote the upstream artifact as it exists -- the Ruby test's
  own name or body, the HTML paragraph as it reads in a browser -- so
  claims stay reviewable against upstream, and drift detection measures
  upstream drift rather than drift in our converter's output.
* A converter's imperfections stay presentational. Under transliteration
  a mis-converted paragraph becomes a wrong block boundary, a failed
  claim, and a wrong denominator; under a native adapter the same defect
  is a cosmetic flaw in a generated view.
* The payoff of transliteration -- the whole site pipeline for free:
  overlay, detail panel, diff, nav -- is kept by having each adapter emit
  a generated AsciiDoc *view* whose blocks correspond one-to-one, in
  order, to the target's blocks (<<_display_views_reverse_engineering_asciidoc,§5>>).
  The view is ephemeral, like the coverage database: generated by every
  scan and build, never committed.

== The target contract

A *target* is one measured file of a scanned repo. An adapter turns it
into:

|===
| Field | Meaning

| `path`
| The repo-relative path as tests write it (`ref/asciidoctor/test/paragraphs_test.rb`)

| `blocks[]`
| In document order; each has a `kind`, a source `span` (1-based line range), a `text`, and the `section` it belongs to

| `sections[]`
| A tree of `(anchor, title, span)`; anchors follow AsciiDoc's auto-id scheme unless the format supplies its own ids

| `defaults`
| Per `kind`: _normative_ (uncovered until claimed) or _non-normative_
|===

*Text* is the block's *claimable text*: what an excerpt is matched
against after RFC 0001's whitespace collapse. Each adapter defines it
once, as the form a human reviewer of that format reads:

* AsciiDoc: source text with inline markup intact (RFC 0001 §4,
  unchanged).
* Ruby: the block's source text verbatim.
* HTML: the element's text content -- entities decoded, tags dropped --
  because nobody reviews a spec against its markup.

Blocks nest only through sections; a block never contains another block.
Where a format nests block-level content (an HTML `<li>` holding a `<p>`
and a sub-list), the adapter splits it the way `asciidoc-parser` splits a
list item: the item's principal text is one block, and nested items are
their own blocks. Every measured line belongs to at most one block;
lines in no block (blank, delimiters, closing tags) are omitted from the
Codecov projection exactly as RFC 0001 §7 omits them.

The `kind` vocabulary is shared where meanings coincide (`paragraph`,
`list-item`, `listing`, `table`, `heading`) and adapter-specific where
they do not (`test-case`, `boilerplate`). Structural defaults are stated
per kind, so RFC 0001 §5's "listings and block titles are non-normative"
becomes one adapter's table rather than a global rule.

Path resolution is widened in one place: RFC 0001 §4 resolves a claim's
path by suffix match against catalog pages sourced from the scan entry's
repo; it now also matches the entry's declared targets
(<<_configuration_and_scoping,§7>>). Targets are files of the scanned
repo, so they version with it: each measured rev carries its own
snapshot, and a claim resolves per rev exactly as RFC 0001 resolves per
page version.

== Adapters

=== AsciiDoc pages

RFC 0001 as written, restated as an adapter: blocks and spans from
the always-on source map of `asciidoc-parser`, text is source with markup,
anchors are the document's section ids, and the defaults table is RFC
0001 §5's. No behavior changes.

=== Ruby test suites

For minitest-style suites as Asciidoctor writes them:

* `context '...' do` (or `describe`) opens a *section*, closed by its
  matching `end`. Anchor: the AsciiDoc-style slug of the context titles
  from the file root down (`_paragraphs_normal`), so `#anchor` claims
  look the same as on spec pages.
* `test '...' do` (or `it`) through its matching `end` is one block of
  kind `test-case`. Its text is the whole test source, so an excerpt may
  be the test's name string alone, a distinctive assertion, or any
  contiguous run of the body. The name is the intended common case:
+
[source,rust]
----
verifies!(
    "ref/asciidoctor/test/paragraphs_test.rb",
    "should treat plain text separated by blank lines as paragraphs"
);
----
+
A name repeated within one file is ambiguous under RFC 0001's rules and
is disambiguated with a `#context` anchor, as on spec pages. In the
v2.0.26 suite every name is unique within its own context; 5 of the 25
files reuse a name across sibling contexts (`api_test.rb` runs the same
three tests under both `Load` and `Convert`), and only those claims
need the anchor.
* Everything else -- `require` lines, helper `def` methods, `context`
  open and close lines, comments between tests -- collects into
  `boilerplate` blocks, one per maximal run.

Defaults: `test-case` is normative; `boilerplate` is non-normative. That
alone fixes the misfiling RFC 0001 §1 complains about: the DocBook tests
the ported modules reproduce inside `non_normative!` today are normative
test cases that we deliberately do not implement, and they become
`out-of-scope` sidecar entries with a reason, visible beside the
percentage instead of vanishing from it.

*Parsing.* Ruby in general is not worth parsing here; the test DSL is.
Verified against the vendored v2.0.26 suite: every one of its 2,783 tests
and 168 contexts is a single- or double-quoted string literal followed by
`do`, and the files are consistently two-space indented (RuboCop-enforced
upstream). The adapter is therefore an indentation-aware line scanner:
it recognizes the four openers, skips heredoc bodies by their terminator
(`<<~EOS` ... `EOS`, quoted or not), and closes a construct at the first
`end` on the opener's indentation. It fails loudly on anything else (an
`end` at an unexpected depth, an unterminated heredoc, a non-literal
name), so a suite the heuristic does not fit is a scan error, never a
silently wrong denominator. If a second suite ever needs more, the
contract lets the scanner be swapped for a real Ruby parser
(tree-sitter-ruby or Prism bindings) without touching anything downstream.

=== HTML documents

For a specification available only as HTML:

* Parse with `html5ever` (MIT OR Apache-2.0): a real HTML5 tree builder,
  tolerant of the markup specs are actually published with. Line spans
  come from the tree-sink callback `set_current_line`, which the parser
  invokes whenever the source line changes; the adapter's own sink
  records the open and close lines of every element. (`scraper`, the
  usual convenience layer, is ISC-licensed and fine, but it discards
  line information, so the adapter implements the thin sink itself.)
* *Blocks* are block-level elements with direct inline content: `p`,
  `li` and `dt`/`dd` principal text, `pre`, `blockquote` paragraphs,
  `figcaption`, a `table` as a single block, headings, and any `div`
  whose children are inline. Kinds map onto the shared vocabulary.
* *Sections* follow the heading hierarchy (`h1`-`h6`, or `<section>`
  elements with a heading). *Anchors* are the document's own `id`
  attributes where present -- HTML specs have them on nearly every
  heading -- so a `#anchor` claim is also a working upstream fragment
  URL; elements without an id get an AsciiDoc-style slug of the heading
  text.
* *Text* is text content with `script`, `style`, and `template` content
  dropped, `br` read as a space, entities decoded, whitespace collapsed.

Defaults: paragraphs, list items, description terms and definitions, and
tables are normative; `pre`, headings, captions, and figures are
non-normative -- the HTML rendering of RFC 0001 §5's table.

== Display views: reverse-engineering AsciiDoc

Can AsciiDoc be recovered from HTML? In general, only lossily: HTML
carries presentational structure AsciiDoc has no words for, inline
markup does not round-trip exactly, and every existing converter (pandoc
among them) produces output whose quality varies by construct and whose
shape changes across converter versions. That is why
<<_design_overview,§2>> refuses to make a converted `.adoc` the source of
truth. For *display*, however, lossy is acceptable, and the loss can be
bounded.

Each adapter emits a generated AsciiDoc view built under one invariant:
*one view block per target block, in order.* The build parses the view
like any page, pairs its blocks with the target's by position, and
attaches states -- so the overlay, the detail panel with click-through,
the diff against the previous snapshot, and nav all work with no second
mapping. The Codecov export ignores the view entirely and projects onto
the target's own lines (<<_codecov_export_and_parity,§9>>).

*Ruby view.* One page per test file: a section per `context`, a
`[source,ruby]` listing per test case titled with the test's name, and a
`[source,ruby]` listing per boilerplate run (dimmed as non-normative).
This is the answer to "and maybe even the Ruby": yes, and cheaply,
because the suite's structure is regular. A richer rendering -- each
test as an example block showing its AsciiDoc input heredoc as
`[source,asciidoc]` beside its assertions -- is a later refinement of
the same view; the coverage unit stays the test case either way.

*HTML view.* One page per document: headings become sections;
paragraphs, lists, description lists, quotes, and `pre` become their
AsciiDoc counterparts; a small inline set (`code`, `em`, `strong`,
`a`, `sub`, `sup`) is converted and any other inline element reduces to
its text; simple tables become AsciiDoc tables. Any block the converter
cannot represent faithfully becomes a passthrough (`pass`) block holding
the sanitized original element (allow-listed tags and attributes, no
scripts, styles, or event handlers). The passthrough fallback is what
makes the one-to-one invariant hold by construction: the converter never
has to drop or merge a block to cope with markup it does not understand.

*Fidelity check.* The view is verified, not trusted. `bokfell coverage
lint` renders each view and compares every rendered block's text content
with its target block's claimable text after normalization; a mismatch
names the block. This catches a converter bug the moment it would
mis-shade something, and it makes the one-to-one invariant testable
rather than aspirational.

Views are never the thing claims quote. A test that copies an excerpt
from a rendered view is quoting text the adapter derived from the
target, and for the AsciiDoc adapter -- where RFC 0001 deliberately keeps
inline markup in the excerpt -- that would be wrong; `lint` warns when a
claim's excerpt matches a view block's text but not its target block's.

== Claims inside ignored tests

Porting the Ruby suite exposed a hole in RFC 0001's static scan. The
ported modules keep tests blocked on unimplemented features as stubs
marked `#[ignore]`, and 64 of the 65 such stubs today carry a
`verifies!` block. RFC 0001 §6 argues that CI's green gate backs every
statically found claim; an ignored test never runs, so its claim is
backed by nothing and would count as verified.

Rule, applying to every adapter: a claim inside a test function carrying
`#[ignore]` resolves its blocks to *planned*, not verified. The tracking link is taken from
the ignore reason when it contains a URL or `owner/repo#N` shorthand
(`#[ignore = "asciidoc-rs/asciidoc-parser#1394"]`); a planned block whose
claim carries no link is reported by `lint`, as is a `planned` sidecar
entry for a block an ignored claim already covers. Removing the
`#[ignore]` when the feature ships promotes the block to verified with no
other edit -- the same "the planned work shipped" transition RFC 0001 §3
defines for a claim landing on a `planned` sidecar entry.

== Configuration and scoping

A `coverage.scan` entry (RFC 0001 §7) gains a `targets` list:

[source,yaml]
----
coverage:
  scan:
    - repo: https://github.com/asciidoc-rs/asciidoc-parser
      tests: [parser/src/tests]
      spec_map: spec-map
      targets:
        - path: ref/asciidoctor/test        # a file or a directory
          kind: ruby-test
          publish:
            module: asciidoctor-tests        # view pages land here
        - path: ref/some-spec/index.html
          kind: html
          publish: false                     # measured, never displayed
----

* `path` names a file or a directory (every file of the adapter's
  extension beneath it). Claims name files by the same repo-relative
  path, matching today's `track_file!` strings, so the RFC 0001 §9
  converter needs no change for Ruby targets.
* `kind` selects the adapter: `asciidoc`, `ruby-test`, `html`. No
  auto-detection; an unknown extension under a `path` is a scan error.
* `publish` places the view pages in the catalog. The view of a target
  file becomes a page of the named module (in the component the scan
  entry's repo contributes to; `component:` may be given explicitly),
  with the file's basename and an `.adoc` suffix, plus a generated nav
  listing the module's views. `publish: false` measures the target and
  shows it on the dashboard with a link to its upstream location, but
  generates no view -- the default for `html`, for the reasons in
  <<_licensing_and_provenance_of_vendored_targets,§8>>.
* View pages join nav and the overlay but are excluded from the search
  index by default (a suite of test bodies swamps search results);
  `publish.search: true` opts in.

Catalog spec pages remain implicit targets, as in RFC 0001: they need no
`targets` entry.

== Licensing and provenance of vendored targets

A target we do not author lives in the implementation repo as a
*snapshot*, and publishing a view of it is redistribution in a modified
form. Two requirements:

. Every vendored target directory carries the upstream `LICENSE` and a
  `SOURCE` manifest recording the upstream URL, version or commit,
  retrieval date, and the snapshot's content hash. `ref/asciidoctor/`
  already does the first two in its README; the manifest makes them
  machine-checkable, and `lint` reports a snapshot whose hash no longer
  matches its manifest.
. `publish` is set only after the license has been read. The Asciidoctor
  suite is MIT and is published with its notice reproduced in the view's
  footer. Many specifications are not: a typical document license permits
  verbatim copying with attribution but not derived works, and an
  AsciiDoc view is a derived work. Such a target is vendored for
  measurement only (`publish: false`), or, where even vendoring is
  disallowed, fetched at scan time from a pinned URL whose content hash
  is recorded in the manifest and never committed. Either way the
  dashboard shows its coverage and links upstream, and nothing of its
  text enters the site.

== Codecov export and parity

RFC 0001 §7's projection rule needs no change: every line of a verified
block emits `1`, every line of a planned, uncovered, or unclassified
block emits `0`, and lines of out-of-scope and non-normative blocks or of
no block are omitted. The keys are target paths, so the existing
`ref/asciidoctor/test/**/*.rb` Codecov component keeps reporting without
a configuration change, and the HTML adapter's element line spans give an
HTML target the same treatment.

Parity with `sdd` for the Ruby files holds at the projection level once
the migration below runs: a test-case block spans the `test` line
through its `end` inclusive, which is exactly the span today's
`verifies!` reproductions quote (minus the blank-line bookkeeping `sdd`
already skips); boilerplate that today sits in `non_normative!` is
omitted by the adapter's defaults instead.

== Migration

RFC 0001 §9's one-shot converter grows two Ruby-specific steps:

. For each `verifies!` reproduction in `parser/src/tests/asciidoctor_rb/`,
  take the path from `track_file!` and the excerpt from the *name* of the
  first `test '...' do` line inside the quoted block -- shorter and more
  stable than quoting the body. Where the name recurs in the file, the
  converter adds the `#context` anchor of the enclosing Rust `mod`
  (the ports mirror Ruby contexts as nested modules, so the anchor is
  derivable). A claim inside an ignored fn is left in place; it
  resolves to `planned` under <<_claims_inside_ignored_tests,§6>>, and the
  converter copies any tracking reference from the stub's `TODO` comment
  into the ignore reason.
. Each `non_normative!` span that contains a `test '...' do` line is not
  boilerplate: it is a test the port deliberately omits. The converter
  emits those as `[[out-of-scope]]` sidecar entries with the reason taken
  from the module's stated convention (DocBook and other non-HTML
  backends; compatibility mode), for the editorial pass to confirm.
  Spans that contain no test are dropped -- the adapter's defaults
  already classify them.

Then, as in RFC 0001 §9: diff Codecov output before and after, confirm
parity, and retire the second `SPEC_SOURCES` root of `sdd` along with
its first.

== Open questions

. *HTML tables.* One block per table matches the AsciiDoc adapter, but
  specification tables often state one rule per row. Start with one
  block and revisit with a real target in hand; a per-row option is a
  contained adapter change.
. *Excerpts across adapters.* An excerpt is matched against source text
  for AsciiDoc and against text content for HTML. That asymmetry is
  deliberate (each is what a reviewer of that format reads) but should
  be re-examined if authors find themselves copying HTML excerpts from
  rendered spec pages rather than from upstream.
. *Ruby scanner scope.* The indentation-aware scanner is sized to the
  Asciidoctor suite. The trigger for adopting a real Ruby parser is the
  first suite it rejects, not speculation.
. *Cross-repo targets.* RFC 0001 lets a claim name a page in another
  component by resource ID. Whether a claim may name another scan
  entry's *target* is left open until a case appears.
